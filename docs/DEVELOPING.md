# Developing Polku

Polku is a static site with no build step and no backend: `index.html`, plain ES modules, and MapLibre GL JS from a CDN. [polku.si](https://polku.si) is served by GitHub Pages from `main`.

What to do is on GitHub: the [issues](https://github.com/TommiContursi/Polku/issues), the [milestones](https://github.com/TommiContursi/Polku/milestones) and the [board](https://github.com/users/TommiContursi/projects/1). The board holds the order of the phases, [ROADMAP.md](ROADMAP.md) what holds for every phase, [plans/](plans/) their designs, and what's shipped in the [changelog](../CHANGELOG.md). This file is how Polku works.

How to work on it (what to work on, testing, pull requests, bugs and findings, writing) is in [AGENTS.md](../AGENTS.md), for people and coding agents alike.

## Bugs and reviews

Each planned phase, and each round of fixes, is a milestone. The board orders the phases.
- `docs/retros/` keeps a short retro for each finished milestone: what cost time, what to keep, and what changed in AGENTS.md because of it.

## Running it

```bash
python3 serve.py        # → http://localhost:8765
```

Any static server works; `serve.py` just turns off HTTP caching while you edit.

With the dev server running and Google Chrome installed:

```bash
python3 tools/smoke.py water loops      # only these groups: the ones a change touches (the whole suite runs on GitHub, below)
python3 tools/smoke.py --list           # every group and size, with what it checks
python3 tools/shoot.py shots after      # screenshots for a pull request (--list for the scenes)
python3 tools/readme_shots.py           # legacy README scenes, into docs/screenshots (WebP)
tools/brouter-local.sh                  # optional: BRouter on this computer (Settings → Routing server)
python3 tools/style_probe.py --presets  # does every route style change the route? (against the local BRouter)
python3 tools/loop_probe.py             # how long do round-trip loops ride? (calibrates js/roundtrip.js)
python3 tools/water_probe.py            # paddling legs before/after the water costs: length, ms, grid cells
```

A session runs the groups its change touches, never the whole suite on this computer. The whole suite runs on GitHub's Ubuntu runner, started by hand, and only once `main`'s suite is green (#579); until then the groups are enough (AGENTS.md, "Testing"). To start it: **Actions → Smoke suite → Run workflow** on any branch, or `gh workflow run smoke.yml --ref <branch>`, with `-f groups="fit quick"` for only some groups. The full suite runs in ten parallel jobs, about 4–16 minutes each; `button3d` and `button3dphone` have one each, as the 3D button's checks took 16–27 minutes as one group (#411); `.github/smoke-shards.json` says which groups each one runs, and a new group goes into one of them, by its time on the runner, or the run fails; `tools/smoke.py` fails the same way before a local run starts (`shard_check()`, #577). The `report` job's summary has every `FAIL` with its lines, the Chrome version, the time per step and the requests to other hosts; each job's log is its `smoke-log-<n>` artifact. The runner is set up like the development Mac (Inter, en-GB, Helsinki time, a mouse) in `.github/workflows/smoke.yml` and `.github/chrome.sh`. It isn't a required check (#268).

The tests answer from recorded files in `tools/fixtures/` (a route, an Overpass tile, LIPAS answers, Väylävirasto fairways), so they make no routing calls. `tools/brouter-local.sh` starts BRouter on your computer for anything that does route; please don't burst-test brouter.de.

A pull request's screenshots: `python3 tools/shoot.py OUTDIR before|after [scenes]` on `main` and on the branch, as JPEG on the `pr-screenshots` branch under `<branch>/`, linked as `https://github.com/TommiContursi/Polku/blob/pr-screenshots/<branch>/<file>.jpg?raw=true`.

The README links JPEGs on the `pr-screenshots` branch. Capture its current scenes with `tools/shoot.py`: `desk-planner`, `desk-trails-close`, `phone-planner`, `desk-trail-headsup` and `desk-water-crossing`. Check the images, convert them to JPEG, put them under the documentation branch's name on `pr-screenshots`, and update the README links. Keep new images off `main`.

Headless Chrome draws the map in software, and one frame can take a second when the computer is busy. So a check waits for the state it tests, not a fixed time: the next animation frame for something the app does in one, `SETTLED` in `tools/smoke.py` for the planner's size. It also runs with reduced motion, so `fitBounds` and `flyTo` fire `moveend` at once: call `map.once('moveend')` before moving the map.

The `otherways` quick-point check schedules its edit in the same turn as the first leg's alternative-route timer, then waits for the final leg's offer. It also blocks the main thread for 2.2 seconds so both timers are overdue, checking that a slow frame preserves their order. Keep the request-count, requested-leg and offered-leg assertions; the separate pause case checks that waiting really does fetch an earlier alternative.

### Writing a smoke check

- A group is a function in `tools/smoke.py` that takes `chrome`, opens a page (`chrome.page(w, h, phone)`, then `pg.open_app(...)`), runs a script with `pg.js(...)` that returns a list of failures, adds `pg.errors()` as console failures, prints `ok` or `FAIL` with them, and returns whether it passed. Add a row to `GROUPS`, just above `main()`: a short name, its functions and a one-line description. `main()` runs from that table and `--list` prints it, so `python3 tools/smoke.py <name>` runs the group alone; a name that isn't in it stops the run before Chrome starts, with exit code 2.
- A group that raises (a script error in the page, Chrome not answering) prints `FAIL` with the error's first line, and the next group still runs, in a fresh Chrome if this one stopped answering. Still catch what you can and say what failed.
- When another run already holds the Chrome profile (`POLKU_CHROME_PROFILE`, or `~/.cache/polku-tools/chrome-profile`), `tools/cdp.py` gives this run a temporary profile, says so in one line, and deletes it afterwards. That run starts without the cached tiles.
- Answer from `tools/fixtures/` (fetched from `location.origin`), and hold or seed the fetches the check doesn't test, as the existing groups do. Never route against brouter.de.
- Do what a user does: click, drag and type on the real controls, not the module's functions.
- Wait for the state you check (the next animation frame, `SETTLED`), never a fixed time. On GitHub's runner the map draws in software and a frame can take a second: a control read before its sheet settled was still moving (#406, #410), and a transition waits for a frame to start, so read a pressed control once it's `:active` and its transition has run (#423).
- On a phone page, tap with `pg.quick_tap()`, a finger up after 50 ms by its own times. `pg.tap()` sends its touchend only once the page has answered the touchstart, which a busy page takes for a held finger (#405).
- `open_app()` and `reload()` return once the map has loaded (`pg.map_loaded()`, 300 s at most: `button3d`'s reloads in 3D took up to 205 s on GitHub's runner; a load over 20 s says how long in the log) and MapLibre's `load` event has run Polku's own load step (the saved route, the planner left open, the layers), 45 s at most. That event comes a frame after the map counts as loaded, and much later on a busy machine; a check that began first had its route drawn again under it (#248). A page or a map that doesn't load raises an error naming what it still waited for: the map's sources still loading and the requests that never answered (`pg.waiting()`, #409). A saved timeline and weather layers open earlier, at start-up, and the map's buttons show only once they're in their place above it (#292), and the timeline keeps the room its reading's lines need from the start, so it doesn't grow when its forecast comes in (#301; `--tl-lines` in `css/app.css`, set by `readout()` in `js/wxmap.js`). `WX_FIXED` answers the forecast with fixed weather, held until `__wx.release()` if `__wx.hold` is set. Before measuring the buttons, wait for `SETTLED`, and take a button's place again right before each tap or click, as `button3d` does. To hold the `load` event back, see `COLUMN_HOLD`.
- A group that doesn't check Paddle's depths gives its pages `EMPTY_DEPTHS`: Traficom's map tiles answer at once, empty. MapLibre draws no frame for a tile that fails (anything but a 404), and it fires `load` and `idle` only at the end of a frame, so a failure that was the map's last load kept Polku's load step from coming at all until `js/main.js` asked for a frame on every tile error (#393). `tilefail` checks that with `DEPTHS_FAIL_LAST`, which holds Traficom's tiles until every other tile is in, then fails them.
- The toolbox is shown and placed in an animation frame after a change. Read it, or measure anything near it, once the sheet has settled and two frames have passed: `placed(pg)` in `tools/smoke.py` (#367, #390).
- A fix's check must fail without the fix: run it on a worktree of `main` first.

## How the trickier parts work

### In-app release notes

- **In-app release notes** (`js/changelog.js`): Settings opens the shared native dialog and requests the deployed `CHANGELOG.md` through `request('polku', …)` only on opening or Retry. The service worker may supply its saved copy, so the view shows the notes’ latest date and an explicit saved-copy label when offline. Headings, paragraphs, bullets, bold text, code and HTTP(S) links are built as DOM nodes; HTML and unsafe URL schemes never execute. Relative links point to the repository. Closing aborts a pending request and restores focus; dialog key events stay out of the map shortcuts.

### The map: style, grades, terrain and trails

- **Optional static OSM selection** (#154): `OSM_DATA_MANIFEST` in `js/config.js` enables `js/osm-data.js` for `loadWays()` in `js/ways.js`. It points to the verified ducksoft.fi snapshot; data publication and app activation are separate operations. Each page pins an immutable release, downloads only needed PMTiles JSON tiles through `request('osmdata', ...)`, and reuses them from IndexedDB. Complete way geometry and ordered node IDs feed the existing `slimWays()`/index; only named route relations supply joining names. Static reads allow 64 growth rounds, versus Overpass's six, with the existing 25 km and junction/name rules. Uncached tiles must fit the attributed extract polygon; uncovered or unavailable tiles fall back to cached Overpass. A pick using public fallback retains the six-round growth budget. Ways and lighting readers share the page’s pinned manifest, including a missing optional dataset. Routing, map tiles and area queries keep their existing paths; the existing detail consumers use the shared hosted selection described below. Build/schema, tests, preview, publication and rollback are in [OSM_DATA.md](OSM_DATA.md); `python3 tools/smoke.py osmdata` checks the client and, when configured, the full northern selection.

- **Style** (`js/style.js`): one function builds the whole MapLibre style from app state and is applied with `setStyle(..., {diff: true})`. Sport, base map and overlays are all just state.
- **The hills' light** (`js/style.js`, #642, #910): the flat map lights the hillshade from four directions (`multidirectional`); 3D with its hills raised from the north-west (`standard`, anchored to the map), while the sky and the buildings' `light` follow the sun, the light from straight above while the sun is down (never MapLibre's own, which turns with the camera) (#644: `ctx.skyAt()`, `SKIES` and `skyOf()` in `js/style.js`, the weather from `weather.sample()` only while a forecast is loaded; `lightStale()` rebuilds the style when the hour, the place or the forecast changes it); 3D with **Raised hills** off (`state.raiseHills`) is tilted with no `style.terrain`, lit as the flat map; with **The sun** (`state.hillLight`) from the sun's direction and height at the timeline's hour (`combined`), from `ctx.sunAt()` in `js/main.js`: `sunPosition()` in `js/sun.js` at the map's middle, the hour rounded to ten minutes. The timeline's `onTime` rebuilds the style when that hour changes. The shadows' tiles keep the last hour (`shadeFor`) until all of theirs are drawn (`shadowsDrawn()`), and `applyStyle()` hands them the new hour with `setTiles()` rather than letting the diff swap the source, so MapLibre keeps them on screen while the next load: a playing timeline steps them as fast as they're worked out (#945). Below 0.5° the fixed light comes back. The colours' transitions are 0: MapLibre can't blend four lights' colour lists with one light's colour, and throws. **Shadows** (`state.hillShadows`) is a raster source, `sunshadow://{z}/{x}/{y}?t=`, from zoom 10 to 13 and overzoomed past it: `js/shadows.js` takes the heights from one tile beyond it on every side from the contour library's `DemSource.getDemTile()` (its cache shared, no request of its own), from the DEM a zoom out: 2 × 2 of its tiles, which the tiles around share (3 × 3 at the same zoom timed out in the library's queue in tilted 3D). Then it sweeps them from the sun's side (`castShadows()` in `js/shadow-sweep.js`, a module worker that also paints the tile's PNG, so a screen of tiles doesn't stall the map): each pixel carries how high a ray from the sun still is, one pixel along the sun's main axis, between two across it, so it's one pass. `shadowPicture()` sweeps the heights at twice the grid's pixels, each between its four nearest, and softens the shadows' edges over 3 × 3 of them, so a tile shown past its zoom has no steps. A tile's shadows reach at most one tile from their hill, so under 3° the Layers line says the shadows reach farther than the map shows. A tile whose heights don't load throws, so MapLibre draws none there, and a toast says some are missing. **The trees' and buildings' shadows** (#919, `state.objectShadows`, a switch of its own) are a second source with the same hour, `sunshadow://{z}/{x}/{y}?t=…&objects`, zoom 14 to 15 (about 2.5 m pixels in southern Finland, swept at half that), overzoomed past it. Its grid is the DEM plus the taller of the trees and the buildings: the trees from Meta and WRI's canopy height map v2 (CC BY 4.0), read from Source Cooperative's copy (`data.source.coop/tge-labs/meta-chm-v2`, CORS and byte ranges; Meta's own bucket has no CORS), one cloud-optimised GeoTIFF per zoom 10 tile named by its quadkey, with 512 px deflate pieces for each zoom 10–16. `js/shadows.js` reads a file's first 128 kB once for where each piece is, then a piece of the zoom a zoom out (as for the DEM), unpacked with `DecompressionStream`: no GeoTIFF library. No file (404) is open water, no trees. These go through `request('canopy')`. The buildings are OpenFreeMap's zoom 14 footprints with `render_height` (5 m where OSM has none), fetched like the map's own tiles (no `request()`, the browser's cache and the offline save have them), read by `decodeBuildings()` and drawn into the grid on an `OffscreenCanvas`. The sweep is given the bare ground too, and leaves out what the ground alone shades: the hills' layer draws that. Both layers are drawn over water and buildings, under the roads. `tools/smoke.py sunlight` checks the sun's place, a wall's shadow, a tree's beside it, Helsinki's footprints, the light over the hours and the zoom 15 tiles.
- **Raster detail** (`js/config.js`, `js/style.js`): the Kapsi terrain base and overlay request 1024-pixel WMS images displayed as 256-pixel tiles, and MML WMTS uses 128-pixel visual tiles, so detailed cartography remains visible farther out. Aerial photos and vector WMS layers use at most 2× display density; WMS also asks for 180 DPI to preserve symbol sizes and scale thresholds. Esri keeps its level-19 cap and requests `blankTile=false`: missing coverage returns 404, letting MapLibre retain or fetch a usable parent rather than draw Esri's no-data picture. Waymarked Trails, weather, ice and elevation keep their own resolution choices.
- **Depth visibility** (`js/config.js`): contours appear from map zoom 10 and soundings from 13. Traficom's contour style has no scale cutoff; its sounding style uses dots between 1:300,000 and 1:40,000, and numbers below 1:40,000. Display density changes the requested pixels and DPI together, not these cartographic thresholds.
- **The route's edge** (`js/style.js`, `edge`): dark on the light maps and white on the night map and the aerial photos, for the lit stretch and the preview. A leg over water has it too on the light maps (`route-casing` is a case on the leg's `mode`), as a white edge is 1.8:1 against Paddle's pale sea (#611). Smoke's `water` group checks 3:1 against the sea's fill on the Trail map and the night map; Maastokartta and the aerial photos have no fill to measure, so they're looked at.
- **Lit ways** (`js/lit.js`, #638): OpenFreeMap's tiles don't carry `lit`, so it comes from the hosted z13 lighting archive when published, with cached Overpass fallback for missing datasets, uncovered tiles or failures. The fallback uses one query per z13 tile (the trail details' grid, `tilesIn()`), through `cachedOverpass()`, from zoom 14 and only while the overlay is on; loaded tiles still draw at 13. Lit is yes, 24/7, automatic, sunset-sunrise, limited or interval, unlit is no or disused, and anything else counts as no tag, which gets no line. The query (`litQuery()`) asks for no tags, as a tile with them was 5.4 MB in Helsinki's centre: the lit ways (`out skel geom`), `out count` as a marker, then the unlit ones, and `slimLit()` keeps `[id, 1 lit or 0 unlit, coords]` from where each way comes. An answer with a remark (a server-side timeout) is no data (`osm.js`, #661), so its tile says No data now rather than looking empty. `style.js` draws lit with the route's kind of edge (dark on the light maps, white on the night map and the aerial photos) and unlit dashed. Overpass is never backed off (`osm.js` passes `backoff: false`), so `sourceStatus('overpass')` can't say it's failing: `LitWays.progress` reports loaded, pending and failed areas for the current view through `onStatus()`. The shared `litStatus()` copy feeds the quick tile, full Layers panel and map-visible `#lit-status` live region. A single ten-second timer changes the waiting message without starting another query; `retry()` clears failed-tile cooldowns, while off/old-view replies cannot revive a hidden status. Successful empty areas count as loaded. The look (`litLook`, Lines or In the dark) is a setting of its own; the overlay is per sport like the others. In the dark is look A, chosen on #638. `lit-veil` is a navy fill over `litCover`, the tiles that came in (`LitWays.publish()`), not a full-screen `background`, so where a tile failed, or nothing has loaded, the map isn't dimmed. It's 45 % on the night map, 55 % on the aerial photos and 70 % on the light maps. `lit-glow` (`line-blur`) and `lit-core` go above it, and labels, the route and the location dot (a DOM marker) stay above them; the unlit dashes are lighter in the dark, for 3:1 over the veil. Its opacity is the shared slider: `opacitySpec('lit')` has no `layers`, so `opacityRow()` rebuilds the style in a frame (as the trail colours' do), and `style.js` scales every lit layer by `overlayOpacity.lit`. The lit layers' opacity transitions are 0, so nothing fades. Smoke's `lit` answers Overpass from `tools/fixtures/lit-laajavuori.json` (the winter tile's lit ways, seeded into its four z13 tiles). A city-centre tile is big: Helsinki's was 5.4 MB raw and 896 KB slimmed on 2026-11-01 (#638).
- **The zoom hint** (`#zoom-hint`, `js/main.js`): shown from zoom 10.5 to 13.8, as the free tiles carry the full trail network from 14. Paddle hides it in CSS on `body[data-activity="paddle"]` (#613), so a change of sport shows or hides it at once.
- **Uphill grades** (`js/uphill.js`): trails in the loaded vector tiles are resampled every 8 m and sampled against the terrarium DEM (`js/dem.js`, bilinear, z14 ≈ 2.3 m/px). They are smoothed over 24 m, cut into ~25 m pieces and graded by the `mtb:scale:uphill` limits (10/15/20/25/30 %). Each piece points uphill, so the arrows point up the climb. Explicit OSM tags win. Graded trails are kept and not graded again, except those a terrain tile failed for: they're graded again on the next map move, so they get their colours once the terrain is back.
- **Terrain that doesn't load** (`js/dem.js`, `js/analysis.js`): each elevation sampling pass keeps up to eight tile loads running, refilling a slot as soon as it finishes. Pending tiles stay shared even when the 220-entry cache evicts completed tiles; completion trims the cache again. A tile request, including its body, is aborted after 15 s; a missing or failed tile falls back to zoom −2 and −4. A tile that failed (network, HTTP error, bad file) is asked for again after 15 s; one that answers 404 isn't. The route's analysis marks where heights are missing (`eleGap`, `terrain`), draws a straight line across a gap, and times the route as flat where nothing is known. The planner analyses the route again after 20 s, then less often, and at once on `online` or Retry, and takes the new analysis once more terrain is in.
- **Trail details** (`js/trails.js`): one Overpass query per z13 tile, cached a week in IndexedDB (`js/osm.js`), gives width, visibility, overgrown and wet stretches, fallen trees, gates, fences and fords. Inside loaded tiles the trails are redrawn from OSM, and the vector tiles' own trails are hidden there with a `within` filter. Along a route, BRouter's `processUnusedTags` returns the same tags for Check.
- **Overpass answers** (`js/osm.js`): HTTP success must also contain an `elements` array and no `remark` before it can win or become the preferred mirror. A racing request tries the remaining mirror if its first three all fail. An explicit `timeoutMs` applies to each mirror, including the racing and remaining requests; unchanged defaults are 25 s for a race and 20 s for sequential requests. The query's server budget and a caller's client budget are separate; callers must choose them together. `python3 tools/smoke.py loading` checks invalid/partial answers, a healthy fourth mirror and caller deadlines with mocked requests.

### Routing on land

- **Routing without a server of our own** (`js/router.js`, `js/net.js`, `js/valhalla.js`):
  - **brouter.de** is a free public BRouter that refuses (403 "Please, retry later!") when one address calls too often. So Polku stays well under it:
    - at most 5 calls in 10 s and 12 a minute;
    - consecutive legs in one call;
    - the routed geometry saved with your route;
    - a drag's live preview only while there's budget to spare.
  - **Valhalla stands in** when brouter.de pauses: the FOSSGIS servers that openstreetmap.org uses, at one call a second at most, as their terms ask. Check says so.
- **Obsolete routing** (`routeAll()`, `js/planner.js`, `js/router.js`): each generation passes one abort signal through its jobs and their fallback jobs. New jobs subscribe before the previous generation is aborted, so a shared request survives while a current subscriber needs it. Cancelled jobs leave the network queue and undispatched planner jobs never start. The same subscriber accounting covers profile uploads and a run joining a leg preview. All land-route cache writes, round trips and Valhalla included, keep the existing 400-entry bound.
- **Separate waits and deadlines** (`js/net.js`): `maxWait` limits queue waiting (the planner allows 6 s before using Valhalla, profile uploads included; a leg refused for pacing that Valhalla can't route either is asked again when its slot comes, from a timer `legFailed()` sets, since pacing sets no back-off and so no `retry` event, #78); `timeoutMs` starts anew for each dispatched attempt and also aborts a stalled response body. BRouter route requests have 120 s, profile files and uploads 15 s, and Valhalla geometry 60 s. A deadline is not a provider refusal and does not trigger a fast retry or outage cooldown. BRouter body timeouts can appear as `AbortError`; the router distinguishes these from its subscriber being cancelled so fallback still works. These deadlines also apply to a configured BRouter; brouter.de's pacing and refusal policy do not.
- **Custom-profile errors** (`js/router.js`, `js/net.js`): normal 403/429 refusal and 5xx backoff still apply. `request()` accepts a `backoff` response predicate for expected 5xx errors only. BRouter 1.7.10 returns an empty HTTP 500 when an uploaded profile file is missing; its exception message goes to server stdout. An empty custom-profile 500 therefore allows one re-upload and route retry. If that re-upload fails, the stock profile routes with its note, as when the first upload fails. The empty response is ambiguous: if the retry also fails, normal backoff applies. Nonempty 500 and other 5xx responses do not trigger a re-upload. Valhalla's optional attributes have a separate 5 s total budget, queue waiting included; expiry returns geometry with unknown tags, while cancellation of the route still propagates. `python3 tools/smoke.py loading pacing` checks these paths with held/mock responses and a scheduling clock, never by bursting public servers.
- **Route dragging** (`js/planner.js`): `onLinePress()` ignores presses originating in MapLibre markers and popups. Markers handle their own drag; starting the line's gesture from the same bubbling press could split the leg twice. `python3 tools/smoke.py editing` checks midpoint-handle and direct-line drags, one new point, Undo/Redo and restored panning with mouse and touch in four sports.
- **Holds on a touch screen** (`bindHold()` and `onLinePress()` in `js/planner.js`): a timer starts each hold (500 ms for the spot's card, 300 ms and then 500 ms on the line, and 60 ms more when it runs, for a lift that a busy page hasn't handled yet), and the touchend and a move can cancel it. On a busy page a timer can run late, or the touchend or a move can reach the page after the time was up, so each compares the touch's own times (`timeStamp`) and not the page's: a finger up before the hold's time was a tap after all (the card closes and the click goes through; on the line `dropEdit()` puts the route back without a step in Undo and the route's card opens), a finger up after it a hold whose timer hadn't run yet (its card opens now), and a move after it, with the timer late, is still the line's drag (#293). - **Route styles** (`js/styles.js`): BRouter's `profile:name=value` parameters override a stock profile's global variables, so most styles need no custom profile. The exceptions are Polku's own profiles, each uploaded once per session: road cycling's `profiles/polku-road.brf` costs gravel main roads as rough, and Short cuts ok (Ways marked private, #106) uses copies of the four stock profiles with an `allow_private` variable (`profiles/polku-hike.brf`, `polku-mtb.brf`, `polku-gravel.brf`, `polku-road-shortcuts.brf`, made by `tools/make_profiles.py`; with it off they route exactly as the stock ones). Every preset was checked to change real routes (`tools/style_probe.py`).

### Water routing

- **Water routing** (`js/water.js`, `js/waterdata.js`):
  - **The grid:** a hidden MapLibre map renders only water, white on black, for the leg's area, and the pixels become a grid. A second drawing on a canvas, in the same projection, marks the costs:
    - Väylävirasto's fairways, by class (shipping lanes are crossed straight);
    - keep-clear zones round danger and cardinal marks and OSM rocks and shoals;
    - places you avoid.
  - **Wind:** each water cell's open-water fetch upwind gives a wave height (JONSWAP), and rough water costs more for the craft.
  - **The path:** A* runs on the grid, and the cell path is string-pulled into straight lines that may not cost more than A*'s way. Land is passable at a high cost, which gives carries.
  - **Slow sources:** each source gets 2.5 s; then the leg is routed without it, Check's Not checked says so, and neither `router.js` nor `water.js` keeps that leg. When the answer comes (`onWaterData`), the planner routes those legs again, and a leg still being routed then is routed once more in `water.js`. A source that failed is asked again two minutes on (`AGAIN_MS`): `onWaterData` tells the planner then too, and routing those legs again asks it (#129). Undo and Redo route again a leg that went without a source, online (#80).
  - **Legs too long to ask for:** a box over 16 of OSM's z11 tiles isn't asked for rocks, nor one over 24 of Väylävirasto's z10 tiles for fairways and marks. `waterInputs()` returns those as `skipped`, apart from `missing`: the leg is kept, nothing asks again, and Check says "not checked, the leg is too long" (`WATER_LONG`, key `waterlong`), and What Polku looked at says so too (#490).
  - **The hidden map's tiles:** a tile that fails (not a 404) asks for a frame, as on the main map (#393), or `load` never came and no water leg was routed (#400). A water tile that doesn't load is drawn as land: the leg may carry where there's water.
  - **No depths.** Traficom's depth data isn't used: its licence excludes route planning. See phase 13 in [plans/done.md](plans/done.md).

### Marked routes from LIPAS

- **LIPAS routes** (`js/lipas.js`, `js/search.js`):
  - **Map data:** z9 tiles intersecting the view supply a natural margin around it. Arrivals are coalesced into one scheduled publication; unchanged visible tiles and late offscreen tiles cause no redraw. The cache retains 64 tiles where possible, keeping current-view and pending entries; Marked routes retains its resolved results even through eviction. WFS requests have a 15 s dispatched deadline. The bound is on retained resolved data, not a global request pool.
  - **Colours:** `LIPAS_TYPES` in `js/config.js` has them, for the line, its label, a picked or lit route, the swatch in the start's list of marked routes and the map key. None is pink or violet (hue 250°–350°): beside the route's magenta they read as its family, and with a thin line's white edge on the night map all the paler (#560). Smoke's `lipas` group checks the hue.
  - **Precision:** geometry comes in EPSG:3067 at full precision and is converted in `js/geo.js`, because LIPAS's EPSG:4326 output is rounded to about 10 m.
  - **One line:** a route's parts are joined at junctions into one line where they can be ridden each once (an Euler path), and ridden as fixed legs, with no routing calls.
  - **Share links** carry those legs as references (`lr=`), not as lines.
  - **Search** asks LIPAS's combined layers by name: three small requests per query.
  - **A place from search** (Photon, #871): `choose()` opens its card once the map has moved (`app.openPlace()` in `js/main.js`), through `openPlaceCard()` with a pin, its kind from Photon's `osm_key` and `osm_value` (kept in recent searches too), and Your route, as every spot's and place's card has (#876). Photon sends no other tags, as a map icon's tile doesn't; an area's pin is Photon's point for it.
  - **Coordinates and a trail from search** (#875): `choose()` opens the spot's card at `r.at` once the map is idle (`app.openSpot()` → `openSpotCard(…, { pin: true })`, as a link to a spot does), so the tiles under it are drawn. A trail's `at` is its point nearest the middle of its bounds (`trailsNamed()`).
  - **Marked routes in view** (the planner's start, `routesIn()`): the layer's own z9 tiles for the sport's route types, asked for whether the layer is on or not and kept in the same cache, so turning the layer on costs nothing more; one entry a place, nearest the map's middle first. A tile that didn't answer counts as failed (said, with Retry, never as none in view); a pause in `net.js` says when it asks again, and the list is made again when LIPAS is back (`lipasBack()`).

  - `al`: another way taken for a leg (#95), BRouter's alternative `k` as `leg:k`, comma-separated; left out when every leg takes its first way.

### The camera, popups and your position

- **Framing above the planner** (`frame()` in `js/planner.js`): every camera move that shows a route, a loop, a stretch or an imported track goes through it, not `map.fitBounds` with padding of its own. - **Where you are** (`js/locate.js`, `js/heading.js`): Polku watches the GPS itself (not MapLibre's geolocate control) and stops while the page is hidden. The dot glides to each fix; while following, each frame moves the map so the dot stays in the middle of the free map (`planner.viewPadding`), and only until it has arrived. The heading is the compass below 1 m/s and the GPS's course above it. Only one feature sends a position, because you ask it to: a round trip from **Where I am** (`loopFromHere()` in `js/planner.js`) asks the browser once and starts the loops there, rounded to five decimals (about a metre, as share links keep every point, #281), so that start is routed like any other point, and kept with the route once a loop is taken. - **The route's moving chevrons** (`js/routeflow.js`, #198): a MapLibre custom WebGL layer over the route line, because a style can't move symbols along a line without laying them out again every frame. The legs go to the GPU as a strip relative to the route's first point (float32 keeps metres there), and the fragment shader draws the chevrons from the along-the-line distance in screen pixels minus time. MapLibre 5 gives custom layers `defaultProjectionData.mainMatrix` for mercator units; `modelViewProjectionMatrix` is for world pixels. Each frame redraws the whole map, so it runs at 24 frames a second at most, only while the route is in view, and rests after 45 s without a touch; reduced motion, 3D terrain and the Settings switch stop it, and the style's static arrows come back (`ctx.flowMoving`). `setStyle(…, { diff: true })` leaves custom layers alone; `styledata` puts it back if a style ever drops it. ### Hosted OSM source selection

`hostedTile(url, dataset, zoom, xy, fallback, {slim, force})` in `js/osm-data.js` shares readers and concurrent source decisions. Ways (z14), lighting/trails (z13), winter/places (z12) and hazards (z11) retain their existing adapters, listeners and failure reporting. Static reads have an eight-second whole-operation deadline. Manifests are pinned per page, reused from IndexedDB for one hour, and failed manifest reads cool down for two minutes. Immutable tiles remain reusable offline; optional datasets absent from the published manifest use the existing seven-day/stale-on-error public caches. Public tile fallback uses one bounded round across the configured independent mirror services (15 s interactive/hazards/places, 30 s background). Successful empty hosted tiles do not call Overpass. Adapted results retain `source.timestamp`, `provider` and `attribution`.

The separate local geometry format in `js/osm-geometry.js` validates schema 2 fragments and area containment seeds. It preserves original node positions/member paths and uses only real source segments for boundary crossings; seeds cannot become display geometry. The compiler API and completeness rules are in [the builder documentation](../tools/osm_data/README.md#local-geometry-format). The registered `osmdata` check also verifies its compiled fixture in both browser sizes. The optional shared product uses the existing static reader/cache and a GeometryCollection of the four country footprints; schema 1 products remain unchanged. Source completeness flags survive sparse empty reads. The build completes original country roots from one same-epoch Europe input before writing local fragments. `geometryTiles()` fetches a bounded local window, coalesces raw reads and rejects conflicting original metadata. `hostedAttempt()` gives multi-stage area/inspection reads one eight-second budget with cancellation. The published manifest still decides whether this optional source is available.

A tile may use the union of equal-epoch country clipping polygons. A vertical sweep checks all boundary-event slabs, including holes and concavities; bounding rectangles and corner samples never prove coverage. Prefer a single covering archive, otherwise remove redundant contributors, read the remaining local ranges in parallel under the same deadline, and check duplicates by original type/ID and complete content. Tile-local road relation subsets merge by original member index with identical original counts/tags and matching overlapping members; full member arrays remain ordered/exact. Country cache entries remain immutable. A required contributor failure, conflicting object or epoch fails the whole hosted result. Union provenance is in `source.sources`, including each country/source; timestamp/provider/attribution remain available. The registered `osmdata` check covers union decoding, fresh-reader offline IndexedDB reuse and failed-contributor fallback.

An explicit path or trail/winter/water/lighting retry resets only a failed shared manifest entry and coalesces one new attempt. That attempt passes `retryDown:true` to `request()`, exempting an existing network-down pause while retaining provider limits and accounting for new responses, including 429/Retry-After. Healthy release pins and cached tiles remain; background cooldowns and other callers keep their existing behavior.

The data build adds exact existing query subsets: non-highway barrier ways and standalone obstacle/ford nodes, ski-only and mapped maintenance ways, water hazard points/ways, and overnight nodes/ways/relations. Place centres are indexed for nearby searches; incomplete referenced place geometry fails the candidate build. New datasets do not appear in production merely because a reader supports them: publication remains separately guarded by the protected workflow described in OSM_DATA.md.

`tools/osm_data/maintenance.py` tracks publisher-owned retention metadata separately from immutable archives. Approved publication protects live/predecessor/latest-two releases and 28 days of successful publications, prunes only validated old owned files, and checks the 80 GiB service budget before upload. Resume targets remain protected. The registered rollback smoke check covers retention pins; full retention tests run in the existing OSM Python CI discovery, and `test-host` exercises the pruner inside its disposable directory.

## Known limits

How Polku works where data or services fall short, with nothing planned to change. Anything that could be changed is an issue (`idea` or `watch`).

- **A building in 3D without a height in OpenStreetMap stands at about 5 m** (#643): OpenFreeMap's `render_height` comes from OSM's `height` or `building:levels`, so towns are mostly right and the countryside's buildings are a default. Better sources are compared in #648; the height is `BUILDING_HEIGHT` in `js/style.js`. **3D buildings** (`state.buildings3d`, #942) leaves them flat in 3D; its switch is in `hillsControls()`, with Raised hills. With the hills raised, MapLibre drapes every flat layer on the terrain under the buildings, so a building in front of the route hides that piece of it.
- **Where the terrain is missing, the route's heights are a guess** (found while fixing #72, 2026-10-15): when no zoom of a terrain tile loads, the height runs in a straight line across the gap, so the climb from one side to the other counts but the hills in between don't, and a gap at the start or end is taken as level. Check, the summary and the dashed line in the profile say so, and Polku keeps trying.
- **Aerial close-up detail is limited by the original photographs.** MML's national orthophoto has 0.5 m pixels. Esri's cached detail varies by place; requesting a higher level does not establish that imagery exists there. The map enlarges the last available image when closer tiles are missing.
- **The trees' shadows are as of the canopy map's pictures** (#919): Meta and WRI's map is from aerial and satellite pictures, in Finland mostly up to 2019 and at the latest 2020, so a forest felled since still casts a shadow and a young one casts too little. It has no species, so birches cast the same shadow in winter as in summer. Under closed canopy the map shows tree tops in the sun, not the path below. Where its pictures meet, along some zoom 15 tile edges, the heights change in a straight line, and so do the shadows (seen at Nuuksio, 2026-11-08: the same in Meta's own files).
- **Trail details have a route budget:** they load on land, gravel and road routes too, even with the layer off. Up to 40 tiles are checked per route; longer routes skip them. Covered tiles prefer hosted data and only use Overpass when that source is unavailable or uncovered.

## The free services: limits and quirks

- **brouter.de pauses busy devices** ("retry later": about 40 s after some 20 calls in 8 s, escalating to about 30 minutes after repeated bursts), and the pause covers the whole connection, the user's too. Never burst-test it: use the local BRouter (`tools/brouter-local.sh`). Valhalla on FOSSGIS stands in.
- **Overpass mirrors are flaky:** 504s on every mirror at times while building phases 12 and 13. Trail details are best-effort and cached; route warnings from BRouter don't depend on it. The water router waits 2.5 s for OSM's rocks, then routes without them (Check's Not checked says so) and routes the leg again when they arrive (#67, #81). If it gets worse, there's an idea for static data built weekly.
- **Free tiers, if Polku gets popular:** Open-Meteo 10 000 calls a day per IP, non-commercial; Overpass 10 000 a day in `net.js`; FMI 20 000 a day; GitHub Pages about 100 GB a month of bandwidth. The counters are in Settings → Data sources.
- **OpenFreeMap's tile URLs change weekly;** saved offline areas use version-free keys (`sw.js`).
- **LIPAS search costs three requests** per query (12c: the combined layers `lipas_kaikki_reitit` / `lipas_kaikki_pisteet` take one filter for every type). If LIPAS renames or drops those layers, search loses its routes and stops (Places still work).
- **Traficom's depth layers** are shown "not for navigation" and never used for routing (its licence). If Traficom changes the licence or asks, the layers can be dropped from Paddle's defaults.

- **A new screen** reuses these for the same jobs. A new control is proposed to the user first, and once chosen it joins this table. 25d's cards propose a few (#355): the plain row with a value, the switch with icons, the warning box and the name field.
- **Every control shares** one focus ring (2 px in `--focus`, set once with `:where(…):focus-visible`, drawn inside a row and a menu's item) and press feedback (`btn`, `tool`, `chip`, `act-chip`, `way-tile`, a switch's buttons and the map's and the top bar's buttons shrink to 97 % for 120 ms while held; none with reduced motion; a row, a menu's item, a sport and a search result turn grey at once, a `tg` switch's track darkens). Every `:hover` is inside `@media (hover: hover)`, so a phone's tapped button doesn't keep it; `tools/smoke.py targets` fails on one that isn't. A control's own rule may move the ring (its offset), never change its colour or width.
- **A finger's 44 px** (#235): on a touch screen (`pointer: coarse`), a control outside the planner that looks smaller keeps its look and takes 44 × 44 px with an `::after` around it (the sport pill, Settings, the timeline's weather buttons, ⋯, ✕ and Play, the trip row's ‹ › and Weather card ›, the legend's fold, a map popup's ✕, the credits' ⓘ, the **Zoom in** note) or a taller box (the search's field, the time slider). `tools/smoke.py targets` measures it as a finger finds it, with `elementFromPoint` through the middle each way.
- **Menus and tooltips move** (DESIGN.md's Motion): `popMenu()` and the sport pill's menu (`openActs()`) grow from their button over `--t-open` (`popMenu()` sets `transform-origin` at the button) and leave over `--t-press`; the toolbar's first tooltip (`tooltip()`) grows over `--t-press`, and while one is shown, or was hidden less than 900 ms ago, the next comes at once, with no wait. A menu that's a sheet of its own (`menu-sheet`) only fades. From the keyboard (`:focus-visible` on the button, or in the menu) they come and go at once (`.instant`), the sport pill's chevron too, and so does a menu opened while another is leaving. A closing `popMenu()` is removed at once, so `.menu-pop` is only ever the open menu, and a copy of it (`.menu-leaving`, inert) fades where it was. The sport pill's menu stays in the page when the pill is drawn again (`renderActivityBar()`), so it isn't drawn in again, and hidden it is still drawn while it fades (`allow-discrete`). A new light, dark or contrast (`applyTheme()`) is drawn once with every transition off (`.restyle` on `<html>`, then a forced style pass), so no button fades its colours behind the panels. `tools/smoke.py controls` checks all of it, by a click and by the keyboard, with and without reduced motion.
- **A panel built again on a change** (Layers, its quick drawer, Settings, the speed editor, the sport menu's craft) wraps the rebuild in `settleControls()` (`js/ui.js`): a control that changed starts from how it was drawn (a switch's `checked` attribute; a segment's, a chip's or a tile's `aria-pressed`, a base map's `aria-checked`, a row's `aria-expanded`; a quick tile's look is its `.qt`'s `on` class), so its own transition runs, and the focus goes back to the control it was on. A control is known across the rebuild by its first `data-*` value where it has one (`data-tile`, `data-base`, `data-craft`, `data-k`, `data-appearance`), else by its words. A switch that doesn't rebuild its panel keeps its attribute in step (`toggle()` in `js/main.js`). What opens in a rebuilt panel fades in only on the tap that opened it, through a one-off class (`enter`: Settings' speeds, `speedNew`; Layers' groups, `layerGroup()`), never when the panel is drawn again or from the keyboard; from the keyboard their chevrons turn at once too (`:focus-visible`).
- **A mock-up** copies the CSS of the controls it uses from `css/app.css`, with the same class names, in a marked block (as `docs/plans/mockups/issue-345-map-cards.html` does), so what the user approves is what gets built. When the app's controls change, the copy is made again.
- **No copies:** no second class for a control that exists (a `card-row` beside `way-tile`, say). A variant of one is a modifier on its class, said in this table.

`inspectionAt()` in `js/inspect.js` reads z14 hosted raw objects in the requested 12/40 m neighbourhood, deduplicating by type/ID. `wayNear()` filters by an exact ID before measuring; an absent ID cannot become a nearer substitute. If the optional inspection product is unavailable, an exact way can reuse the original ways archive's full tags. Nearby way selection needs the all-highway inspection dataset. Exact node/relation tags and unambiguous nearby objects use the inspection archive. Ambiguous nearby relations retain the bounded public query. All hosted inspection reads share one deadline. `areaAt()` uses certified point containment followed by nearby original outlines, with named-first/smallest-bounds ranking and unchanged test seeds. Its full-tag card action reuses the loaded original tags, measuring a way only when the whole outline came. Failed, uncovered or incomplete geometry retains one 15-second public round. The `osmdata` group exercises compiled PMTiles through these actual consumers, valid empties, islands, whole/clipped outlines, source metadata and both-source failure.


Four-country OSM candidates keep separate archives per country. Each manifest dataset
record has `kind`, `country`, `coverage` and source provenance; original Finland keys
remain readable by old clients. `StaticOSM.ready(xy)` chooses an archive only when
its clipping polygon wholly covers that tile. Readers share manifests and archive
indices, validate PMTiles zoom/type/compression and never fetch entire countries.
`bundle.py` refuses conflicting overlapping original IDs or mismatched epochs.
Run the focused OSM tests and the candidate workflow before changing publication.
See `docs/OSM_DATA.md`; a candidate alone does not imply live publication.


OSM maintenance uses `health.py` for actual live four-country consumer checks in
addition to HTTP probes; post-publication failure restores only its saved,
expected-current predecessor and remains a failed run. `alerts.py` separates
update, health and rollback incidents, assigns them to the repository owner,
and deduplicates failure/recovery. The notification workflow runs trusted main
only; PR/fork data never selects checked-out code or gains issue-write access.
The existing registered publication guard test covers main-only automatic
writes; all helper tests run in OSM CI discovery. See OSM_DATA.md for activation
and the delivery-test operations.

Manual publication recovery takes a numeric main build run ID in the existing
release input. `publish.recovery_source()` checks completed trusted-main metadata,
successful snapshot/four-country/bundle jobs and a unique unexpired artifact before
download. A failed publish can reuse its successful bundle; rollback by release ID
is independent of artifact expiry.

Retention exposes its validated `previous_release` to same-current publication
resume. The publisher checks that immutable predecessor's manifest and retains
its pointer for post-publication health recovery, including interrupted receipts.

Publication jobs allow 120 minutes for the observed slow artifact download,
full upload/readback and possible guarded rollback. Browser verification still
has its separate 180-second deadline; standalone rollback remains 90 minutes.
