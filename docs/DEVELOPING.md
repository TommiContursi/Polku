# Developing Polku

Polku is a static site with no build step and no backend: `index.html`, plain ES modules, and MapLibre GL JS from a CDN. [polku.si](https://polku.si) is served by GitHub Pages from `main`.

What to do is on GitHub: the [issues](https://github.com/TommiContursi/Polku/issues), the [milestones](https://github.com/TommiContursi/Polku/milestones) and the [board](https://github.com/users/TommiContursi/projects/1). The board holds the order of the phases, [ROADMAP.md](ROADMAP.md) what holds for every phase, [plans/](plans/) their designs, and what's shipped in the [changelog](../CHANGELOG.md). This file is how Polku works.

How to work on it (what to work on, testing, pull requests, bugs and findings, writing) is in [AGENTS.md](../AGENTS.md), for people and coding agents alike.

## Bugs and reviews

Each planned phase, and each round of fixes, is a milestone. The board orders the phases.
- `docs/retros/` keeps a short retro for each finished milestone: what cost time, what to keep, and what changed in AGENTS.md because of it.

## Running it

```bash
python3 serve.py        # → http://localhost:8765
```

Any static server works; `serve.py` just turns off HTTP caching while you edit.

With the dev server running and Google Chrome installed:

```bash
python3 tools/smoke.py water loops      # only these groups: the ones a change touches (the whole suite runs on GitHub, below)
python3 tools/smoke.py --list           # every group and size, with what it checks
python3 tools/shoot.py shots after      # screenshots for a pull request (--list for the scenes)
python3 tools/readme_shots.py           # legacy README scenes, into docs/screenshots (WebP)
tools/brouter-local.sh                  # optional: BRouter on this computer (Settings → Routing server)
python3 tools/style_probe.py --presets  # does every route style change the route? (against the local BRouter)
python3 tools/loop_probe.py             # how long do round-trip loops ride? (calibrates js/roundtrip.js)
python3 tools/water_probe.py            # paddling legs before/after the water costs: length, ms, grid cells
```

A session runs the groups its change touches, never the whole suite on this computer. The whole suite runs on GitHub's Ubuntu runner, started by hand, and only once `main`'s suite is green (#579); until then the groups are enough (AGENTS.md, "Testing"). To start it: **Actions → Smoke suite → Run workflow** on any branch, or `gh workflow run smoke.yml --ref <branch>`, with `-f groups="fit quick"` for only some groups. The full suite runs in ten parallel jobs, about 4–16 minutes each; `button3d` and `button3dphone` have one each, as the 3D button's checks took 16–27 minutes as one group (#411); `.github/smoke-shards.json` says which groups each one runs, and a new group goes into one of them, by its time on the runner, or the run fails; `tools/smoke.py` fails the same way before a local run starts (`shard_check()`, #577). The `report` job's summary has every `FAIL` with its lines, the Chrome version, the time per step and the requests to other hosts; each job's log is its `smoke-log-<n>` artifact. The runner is set up like the development Mac (Inter, en-GB, Helsinki time, a mouse) in `.github/workflows/smoke.yml` and `.github/chrome.sh`. It isn't a required check (#268).

The tests answer from recorded files in `tools/fixtures/` (a route, an Overpass tile, LIPAS answers, Väylävirasto fairways), so they make no routing calls. `tools/brouter-local.sh` starts BRouter on your computer for anything that does route; please don't burst-test brouter.de.

A pull request's screenshots: `python3 tools/shoot.py OUTDIR before|after [scenes]` on `main` and on the branch, as JPEG on the `pr-screenshots` branch under `<branch>/`, linked as `https://github.com/TommiContursi/Polku/blob/pr-screenshots/<branch>/<file>.jpg?raw=true`.

The README links JPEGs on the `pr-screenshots` branch. Capture its current scenes with `tools/shoot.py`: `desk-planner`, `desk-trails-close`, `phone-planner`, `desk-trail-headsup` and `desk-water-crossing`. Check the images, convert them to JPEG, put them under the documentation branch's name on `pr-screenshots`, and update the README links. Keep new images off `main`.

Headless Chrome draws the map in software, and one frame can take a second when the computer is busy. So a check waits for the state it tests, not a fixed time: the next animation frame for something the app does in one, `SETTLED` in `tools/smoke.py` for the planner's size. It also runs with reduced motion, so `fitBounds` and `flyTo` fire `moveend` at once: call `map.once('moveend')` before moving the map.

The `otherways` quick-point check schedules its edit in the same turn as the first leg's alternative-route timer, then waits for the final leg's offer. It also blocks the main thread for 2.2 seconds so both timers are overdue, checking that a slow frame preserves their order. Keep the request-count, requested-leg and offered-leg assertions; the separate pause case checks that waiting really does fetch an earlier alternative.

### Writing a smoke check

- A group is a function in `tools/smoke.py` that takes `chrome`, opens a page (`chrome.page(w, h, phone)`, then `pg.open_app(...)`), runs a script with `pg.js(...)` that returns a list of failures, adds `pg.errors()` as console failures, prints `ok` or `FAIL` with them, and returns whether it passed. Add a row to `GROUPS`, just above `main()`: a short name, its functions and a one-line description. `main()` runs from that table and `--list` prints it, so `python3 tools/smoke.py <name>` runs the group alone; a name that isn't in it stops the run before Chrome starts, with exit code 2.
- A group that raises (a script error in the page, Chrome not answering) prints `FAIL` with the error's first line, and the next group still runs, in a fresh Chrome if this one stopped answering. Still catch what you can and say what failed.
- When another run already holds the Chrome profile (`POLKU_CHROME_PROFILE`, or `~/.cache/polku-tools/chrome-profile`), `tools/cdp.py` gives this run a temporary profile, says so in one line, and deletes it afterwards. That run starts without the cached tiles.
- Answer from `tools/fixtures/` (fetched from `location.origin`), and hold or seed the fetches the check doesn't test, as the existing groups do. Never route against brouter.de.
- Do what a user does: click, drag and type on the real controls, not the module's functions.
- Wait for the state you check (the next animation frame, `SETTLED`), never a fixed time. On GitHub's runner the map draws in software and a frame can take a second: a control read before its sheet settled was still moving (#406, #410), and a transition waits for a frame to start, so read a pressed control once it's `:active` and its transition has run (#423).
- On a phone page, tap with `pg.quick_tap()`, a finger up after 50 ms by its own times. `pg.tap()` sends its touchend only once the page has answered the touchstart, which a busy page takes for a held finger (#405).
- `open_app()` and `reload()` return once the map has loaded (`pg.map_loaded()`, 300 s at most: `button3d`'s reloads in 3D took up to 205 s on GitHub's runner; a load over 20 s says how long in the log) and MapLibre's `load` event has run Polku's own load step (the saved route, the planner left open, the layers), 45 s at most. That event comes a frame after the map counts as loaded, and much later on a busy machine; a check that began first had its route drawn again under it (#248). A page or a map that doesn't load raises an error naming what it still waited for: the map's sources still loading and the requests that never answered (`pg.waiting()`, #409). A saved timeline and weather layers open earlier, at start-up, and the map's buttons show only once they're in their place above it (#292), and the timeline keeps the room its reading's lines need from the start, so it doesn't grow when its forecast comes in (#301; `--tl-lines` in `css/app.css`, set by `readout()` in `js/wxmap.js`). `WX_FIXED` answers the forecast with fixed weather, held until `__wx.release()` if `__wx.hold` is set. Before measuring the buttons, wait for `SETTLED`, and take a button's place again right before each tap or click, as `button3d` does. To hold the `load` event back, see `COLUMN_HOLD`.
- A group that doesn't check Paddle's depths gives its pages `EMPTY_DEPTHS`: Traficom's map tiles answer at once, empty. MapLibre draws no frame for a tile that fails (anything but a 404), and it fires `load` and `idle` only at the end of a frame, so a failure that was the map's last load kept Polku's load step from coming at all until `js/main.js` asked for a frame on every tile error (#393). `tilefail` checks that with `DEPTHS_FAIL_LAST`, which holds Traficom's tiles until every other tile is in, then fails them.
- The toolbox is shown and placed in an animation frame after a change. Read it, or measure anything near it, once the sheet has settled and two frames have passed: `placed(pg)` in `tools/smoke.py` (#367, #390).
- A fix's check must fail without the fix: run it on a worktree of `main` first.

## How the trickier parts work

### In-app release notes

- **In-app release notes** (`js/changelog.js`): Settings opens the shared native dialog and requests the deployed `CHANGELOG.md` through `request('polku', …)` only on opening or Retry. The service worker may supply its saved copy, so the view shows the notes’ latest date and an explicit saved-copy label when offline. Headings, paragraphs, bullets, bold text, code and HTTP(S) links are built as DOM nodes; HTML and unsafe URL schemes never execute. Relative links point to the repository. Closing aborts a pending request and restores focus; dialog key events stay out of the map shortcuts.

### The map: style, grades, terrain and trails

- **Style** (`js/style.js`): one function builds the whole MapLibre style from app state and is applied with `setStyle(..., {diff: true})`. Sport, base map and overlays are all just state.
- **The route's edge** (`js/style.js`, `edge`): dark on the light maps and white on the night map and the aerial photos, for the lit stretch and the preview. A leg over water has it too on the light maps (`route-casing` is a case on the leg's `mode`), as a white edge is 1.8:1 against Paddle's pale sea (#611). Smoke's `water` group checks 3:1 against the sea's fill on the Trail map and the night map; Maastokartta and the aerial photos have no fill to measure, so they're looked at.
- **The zoom hint** (`#zoom-hint`, `js/main.js`): shown from zoom 10.5 to 13.8, as the free tiles carry the full trail network from 14. Paddle hides it in CSS on `body[data-activity="paddle"]` (#613), so a change of sport shows or hides it at once.
- **Uphill grades** (`js/uphill.js`): trails in the loaded vector tiles are resampled every 8 m and sampled against the terrarium DEM (`js/dem.js`, bilinear, z14 ≈ 2.3 m/px). They are smoothed over 24 m, cut into ~25 m pieces and graded by the `mtb:scale:uphill` limits (10/15/20/25/30 %). Each piece points uphill, so the arrows point up the climb. Explicit OSM tags win. Graded trails are kept and not graded again, except those a terrain tile failed for: they're graded again on the next map move, so they get their colours once the terrain is back.
- **Terrain that doesn't load** (`js/dem.js`, `js/analysis.js`): a missing tile falls back to zoom −2 and −4. A tile that failed (network, HTTP error, bad file) is asked for again after 15 s; one that answers 404 isn't. The route's analysis marks where heights are missing (`eleGap`, `terrain`), draws a straight line across a gap, and times the route as flat where nothing is known. The planner analyses the route again after 20 s, then less often, and at once on `online` or Retry, and takes the new analysis once more terrain is in.
- **Trail details** (`js/trails.js`): one Overpass query per z13 tile, cached a week in IndexedDB (`js/osm.js`), gives width, visibility, overgrown and wet stretches, fallen trees, gates, fences and fords. Inside loaded tiles the trails are redrawn from OSM, and the vector tiles' own trails are hidden there with a `within` filter. Along a route, BRouter's `processUnusedTags` returns the same tags for Check.

### Routing on land

- **Routing without a server of our own** (`js/router.js`, `js/net.js`, `js/valhalla.js`):
  - **brouter.de** is a free public BRouter that refuses (403 "Please, retry later!") when one address calls too often. So Polku stays well under it:
    - at most 5 calls in 10 s and 12 a minute;
    - consecutive legs in one call;
    - the routed geometry saved with your route;
    - a drag's live preview only while there's budget to spare.
  - **Valhalla stands in** when brouter.de pauses: the FOSSGIS servers that openstreetmap.org uses, at one call a second at most, as their terms ask. Check says so.
- **Route dragging** (`js/planner.js`): `onLinePress()` ignores presses originating in MapLibre markers and popups. Markers handle their own drag; starting the line's gesture from the same bubbling press could split the leg twice. `python3 tools/smoke.py editing` checks midpoint-handle and direct-line drags, one new point, Undo/Redo and restored panning with mouse and touch in four sports.
- **Holds on a touch screen** (`bindHold()` and `onLinePress()` in `js/planner.js`): a timer starts each hold (500 ms for the spot's card, 300 ms and then 500 ms on the line, and 60 ms more when it runs, for a lift that a busy page hasn't handled yet), and the touchend and a move can cancel it. On a busy page a timer can run late, or the touchend or a move can reach the page after the time was up, so each compares the touch's own times (`timeStamp`) and not the page's: a finger up before the hold's time was a tap after all (the card closes and the click goes through; on the line `dropEdit()` puts the route back without a step in Undo and the route's card opens), a finger up after it a hold whose timer hadn't run yet (its card opens now), and a move after it, with the timer late, is still the line's drag (#293). A hold's lift sends no click (`preventDefault()`, then `noClickUntil`, which the map's own cards honour too): it would land on the card, moved under the finger. `python3 tools/smoke.py routemenu` sends a quick tap with `Page.quick_tap()` from `tools/cdp.py`: its touchend reaches the page only once the hold's timer has run, and carries the time the finger came up. `spotcard` sends held and moving fingers with `Page.touch()`. `Page.tap()` waits for the page's answer to the touchstart before it lifts the finger, so on a page busy for half a second it is a hold (the spot's card): a check that taps the map uses `quick_tap()`.
- **Route styles** (`js/styles.js`): BRouter's `profile:name=value` parameters override a stock profile's global variables, so most styles need no custom profile. The exceptions are Polku's own profiles, each uploaded once per session: road cycling's `profiles/polku-road.brf` costs gravel main roads as rough, and Short cuts ok (Ways marked private, #106) uses copies of the four stock profiles with an `allow_private` variable (`profiles/polku-hike.brf`, `polku-mtb.brf`, `polku-gravel.brf`, `polku-road-shortcuts.brf`, made by `tools/make_profiles.py`; with it off they route exactly as the stock ones). Every preset was checked to change real routes (`tools/style_probe.py`).

### Water routing

- **Water routing** (`js/water.js`, `js/waterdata.js`):
  - **The grid:** a hidden MapLibre map renders only water, white on black, for the leg's area, and the pixels become a grid. A second drawing on a canvas, in the same projection, marks the costs:
    - Väylävirasto's fairways, by class (shipping lanes are crossed straight);
    - keep-clear zones round danger and cardinal marks and OSM rocks and shoals;
    - places you avoid.
  - **Wind:** each water cell's open-water fetch upwind gives a wave height (JONSWAP), and rough water costs more for the craft.
  - **The path:** A* runs on the grid, and the cell path is string-pulled into straight lines that may not cost more than A*'s way. Land is passable at a high cost, which gives carries.
  - **Slow sources:** each source gets 2.5 s; then the leg is routed without it, Check's Not checked says so, and neither `router.js` nor `water.js` keeps that leg. When the answer comes (`onWaterData`), the planner routes those legs again, and a leg still being routed then is routed once more in `water.js`.
  - **No depths.** Traficom's depth data isn't used: its licence excludes route planning. See phase 13 in [plans/done.md](plans/done.md).

### Marked routes from LIPAS

- **LIPAS routes** (`js/lipas.js`, `js/search.js`):
  - **Colours:** `LIPAS_TYPES` in `js/config.js` has them, for the line, its label, a picked or lit route, the swatch in the start's list of marked routes and the map key. None is pink or violet (hue 250°–350°): beside the route's magenta they read as its family, and with a thin line's white edge on the night map all the paler (#560). Smoke's `lipas` group checks the hue.
  - **Precision:** geometry comes in EPSG:3067 at full precision and is converted in `js/geo.js`, because LIPAS's EPSG:4326 output is rounded to about 10 m.
  - **One line:** a route's parts are joined at junctions into one line where they can be ridden each once (an Euler path), and ridden as fixed legs, with no routing calls.
  - **Share links** carry those legs as references (`lr=`), not as lines.
  - **Search** asks LIPAS's combined layers by name: three small requests per query.
  - **Marked routes in view** (the planner's start, `routesIn()`): the layer's own z9 tiles for the sport's route types, asked for whether the layer is on or not and kept in the same cache, so turning the layer on costs nothing more; one entry a place, nearest the map's middle first. A tile that didn't answer counts as failed (said, with Retry, never as none in view); a pause in `net.js` says when it asks again, and the list is made again when LIPAS is back (`lipasBack()`).

### Check's warnings

- **Check's groups** (`js/planner.js`, 25d's Journey C, #233):
  - **Where each item is made:** every maker gives its items `tier` (`'read'`, Read before you go, or `'look'`, Worth a look) and `src` (`{ kind: 'live' | 'map' | 'estimate' | 'calculated' | 'router', by, at? }`): `findWarnings()`, `accessRow()` and `trailWarnings()` in `js/analysis.js`, `hazardsAlong()` in `js/safety.js`, and the planner's own makers. `headsUp(a)` gathers them, with the router's own items (`routerWarnings()`), into `{ read, look, not, hidden }`, each group in order along the route. An item without a tier goes to Read and logs a console error, so a check fails.
  - **Not checked** (`notChecked(a)`): a source that didn't answer is kept on the analysis until it answers, so a late note can't replace it (#265): `a.terrain`, the water legs' `missing`, `a.hazardsError` (only for a route on land in Finland, `fintrafficHere()`), `a.trailError` (where the trail tiles didn't load, from `detailsAlong()`'s `a.tdLost`), `a.winterError` and `a.windError`. Each entry has its Retry, which asks again at once (`forgetFailures()` and its kin drop the couple of minutes a failed tile waits), and `ranges` where it left a gap, which the map dashes. `lookedAt(a)` lists each source as ✓, ? or — for What Polku looked at.
  - **An item's card** (`itemCard()` in `js/cards.js`, `openItemCard()`): items are found again by `itemKey()` (group, words, place), since each analysis makes them anew; `itemsAlong()` is the order ‹ › step in, whole-route Not checked last. Its stretch is lit through `routeLit` (`focusRange()`, #84), no closer than the map was. Everything lit goes through `showLit()` in `js/planner.js` (a leg, a stretch, a climb, an item): `route-lit` draws it over the route in its legs' colour, and `setData()` in `js/main.js` fades the route's own layers while `routeLit` holds anything (`routeDim()` in `js/style.js`, #83). With no route left (Clear route, Undo back to a point) the stretch, its short cut and Check's items go (`runAnalysis()`, #126), so the card closes. On a desktop a card from Check opens beside the panel at its row.
  - **On the map** (`drawHeads()`, `js/style.js`, `js/icons.js`): the `heads` source is clustered (`sev` the most serious); the open item is in `headsOn`, apart and ringed, with its obstacle's own icon (#85); `headsGaps` the dashed stretches. The marker images are drawn with `WARN_COLORS` and named with them, so a new theme draws new ones. With the planner put away, `js/inspect.js` gives a click on a marker to `openHead()` first.
  - **Marking read** (chosen 2026-10-23): `readKeys` holds the items read, by `readKey()` (group, words, place to about 10 m), so an item stays read while it's the same through an edit and a changed one (new words, a later time) is unread. It's saved with the route (`read` in `save()`), not in share links; a new route starts empty, and so does every flow that puts another route in place (`loadTrack()`, a round trip, a LIPAS route, `restoreSnapshot()`, a link): `freshRead()` keeps what was read on the one before on the Undo step, and `undo()`/`redo()` swap them. `restoreSnapshot()`'s step keeps the departure of the route before the same way, as `leave` (its `leavePassed` when that had passed). A source that answers drops its own read marks and saves (`answered()`), so its next failure is new, after a reload too.
  - **Through a new analysis** of the same route (the terrain came, Undo), an item's card keeps its last item while the sources are asked again (`itemKept()`), rather than closing until Fintraffic answers; a kind hidden closes it. Meanwhile `renderWarnings()` keeps it in `headsList` at its place, so ‹ ›, its ring and Got it find it.
  - **Retry** (`notChecked()`'s `ask()`): `a.asking` holds the sources being asked again, so a card built meanwhile still says "Asking…"; Check is drawn again once it's answered.
  - **Markers clear of the DOM's:** the points and the legs' handles are DOM markers over the map, so `drawHeads()` moves an item's marker along the route to the nearest spot 22 px from them, at this zoom (again on `zoomend`); a press on a marker over the line is the marker's (`onLinePress()`), not a new point.
  - **The peek's row, narrow or short** (300 px or less wide, 200 % on a phone; or 300 px or less high, a phone on its side at 150 or 200 %, #438): the count alone moves into the numbers row, so it adds no height. Narrow, it's beside the distance above Done (`.sheet-row.with-count`); short, before Done in the numbers' line, which close up as on a 360 px phone (`.count-inline`). ✕ is left out there, and Check's All read marks them all.
  - **At the profile size** (the numbers and the elevation chart) the full row folds away, as the stats row does, so the chart keeps its room under the 45 % cap (#444); the narrow count stays. The header's ResizeObserver measures the peek again when the row comes back.
  - **Framed again when the peek grows:** within a minute of `fitRoute()`, a taller or shorter peek (the row coming in late) frames the route once more (`fitAt`, in `bindSheet()`'s `sizes()`), unless a card is open. Moving the map, `frame()`, a press on the map or a marker on it (mousedown or touchstart on its container), any edit (`commit()`) and a card opened cancel it, even in the rest of the task that queued it (it runs only while `fitAt` is still the one that queued it), so it never lands under a finger or a card (#446, #467, #513). It runs as a microtask, before the next frame is drawn, so no frame shows the route under the sheet when the peek grows (step 3 of #233: ⌄'s row comes with a route).

### Along the route: marks, departure and colour breakdowns

- **Distance marks** (`drawMarks()` in `js/planner.js`): use the same timed samples as the profile, including stops and changeovers, preferring the wind-adjusted times once available. The existing `routeMarks` setting has `km`, `time` (arrival) and `duration` (elapsed); missing fields default on, and saved values still win. Arrival uses the selected departure immediately, even while the forecast is loading. The marks' switches (`renderOnMap()`, `els.onMap`) are under **Your route** in all layers while a route is drawn (`renderLayersPanel()` in `js/main.js`, drawn again when the panel opens and when a route comes or goes).

### Weather

- **Weather** (`js/weather.js`, `js/wxmap.js`):
  - **The grid:** forecasts are fetched per point of a fixed, nested lattice and kept an hour, so small moves reuse them. Open-Meteo counts every location as a call. The request budget uses short-forecast keys for every point, including pending cells and the same locations at different lattice levels. Camera stops keep the previous zoom even before the first grid arrives, so a cold zoom-out gets the same 1.2-second debounce as a loaded view; pans and zoom-ins retain the 0.6-second delay. `python3 tools/smoke.py weather` checks both paths with mocked forecasts and a scheduling clock.
  - **Along the route:** the route is timed without wind, the forecast is sampled at each point for the hour you'd be there, and the time is estimated again with the head- and tailwind.
  - **Past the forecast** (#465): `windAlong()` gives `beyond`, the first sample past the forecast's last hour (its values there are that hour's), and leaves the wind out of the time from there (`head`, `cross` 0). Nothing reads those values: the weather's colours are grey there (`colorAt()`, `NO_FORECAST` in `js/chart.js`) and the profile marks the cut (`.nofc`); `notChecked()` says No forecast yet from km … (or for this trip, `beyond` 0); the winter and cold checks (`known()` in `winterWarnings()`), the days (`dayWeather()`), Go's weather (`renderWind()`), a section's weather and the key facts look only before it. The water router's wind (`windAt()` in `js/waterdata.js`) is from the 10-day forecast more than two days ahead, and none past its last hour, so no wave is judged by it.
  - **Radar "now"** is FMI's replacement `radar_finland_cappi_rate` GeoTIFF, decoded in the browser. Its default `raster` style stretches bytes per view, so `radar.js` requests a fixed extended SLD colour encoding instead. Read the TIFF's palette colours back to mm/h; palette indexes are arbitrary. White is missing coverage, while dry weather has its own colour. Polku then applies its own rain colours and speckle filter. The reflectivity layer remains a fallback, and FMI request limits still stop both paths. The [source checks](reviews/2026-10-17-radar.md) record the units, quantization and no-data evidence; `python3 tools/smoke.py radar` uses recorded samples and mocked failures.

### Share links and offline

- **Share links** (`shareUrl()` and `parseShared()` in `js/planner.js`): the route in the query string. A part that's empty or the default is left out, and links from before a part was added still open.
  - `r`: the points (an encoded polyline, 5 decimals); `m`: each leg's mode (`a` routed, `l` straight, `w` water); `a`: the sport.
  - `p`, `ps`: the route's style, and legs with their own. `s`: each leg's sport; `cw`: changeover minutes you set.
  - `st`: stops and nights (in `js/stops.js`: `3:60` a break, `5:n0800` a night, `7:n0700x2` a stay of two nights); `cg`: points where the gear goes along. `lr`: LIPAS legs as references.
  - `lv`: when you leave, in minutes since 1970 (#364's C); none: now. One that has passed opens at now, with a note.
  - `al`: another way taken for a leg (#95), BRouter's alternative `k` as `leg:k`, comma-separated; left out when every leg takes its first way.
  - `av`: places to avoid, `lon_lat_metres` each, comma-separated (`av=24.94012_60.17543_40`), about 24 characters a circle. At most 200 are read; anything that doesn't read as a circle is left out, and a toast says the route may go through it.
  - `ic`: legs drawn straight onto the ice (the water note in winter), by number, comma-separated, so whoever opens the link is told that Polku can't see the ice. Older links have none.
  - A leg in a sport other than `a` travels with the route's style for that sport in `ps`, as a style of its own, so the link routes it as it was.
  - Names of points and of places to avoid stay on the device.
- **Offline** (`js/offline.js`, `sw.js`): the tiles along a route corridor at zoom 5–14 go into Cache Storage, and the service worker serves them when the network is slow (4 s) or gone. OpenFreeMap's weekly tile version is stripped from the cache key. The routed line is saved with the area.

- **Hover** (`js/hover.js`): one `queryRenderedFeatures` call when the pointer rests, never while it moves. It uses the click popup's own layer priority, so the preview always matches the click. ## Known limits

How Polku works where data or services fall short, with nothing planned to change. Anything that could be changed is an issue (`idea` or `watch`).

- **Where the terrain is missing, the route's heights are a guess** (found while fixing #72, 2026-10-15): when no zoom of a terrain tile loads, the height runs in a straight line across the gap, so the climb from one side to the other counts but the hills in between don't, and a gap at the start or end is taken as level. Check, the summary and the dashed line in the profile say so, and Polku keeps trying.
- **Trail details along every route cost Overpass calls** (bug sweep, 2026-10-15): they load for every route on land, gravel and road too (up to 40 tiles a route, cached a week), not only with the map's layer on. Watch the Overpass counter in Settings; a long road route over 40 tiles skips them.

## The free services: limits and quirks

- **brouter.de pauses busy devices** ("retry later": about 40 s after some 20 calls in 8 s, escalating to about 30 minutes after repeated bursts), and the pause covers the whole connection, the user's too. Never burst-test it: use the local BRouter (`tools/brouter-local.sh`). Valhalla on FOSSGIS stands in.
- **Overpass mirrors are flaky:** 504s on every mirror at times while building phases 12 and 13. Trail details are best-effort and cached; route warnings from BRouter don't depend on it. The water router waits 2.5 s for OSM's rocks, then routes without them (Check's Not checked says so) and routes the leg again when they arrive (#67, #81). If it gets worse, there's an idea for static data built weekly.
- **Free tiers, if Polku gets popular:** Open-Meteo 10 000 calls a day per IP, non-commercial; Overpass 10 000 a day in `net.js`; FMI 20 000 a day; GitHub Pages about 100 GB a month of bandwidth. The counters are in Settings → Data sources.
- **OpenFreeMap's tile URLs change weekly;** saved offline areas use version-free keys (`sw.js`).
- **LIPAS search costs three requests** per query (12c: the combined layers `lipas_kaikki_reitit` / `lipas_kaikki_pisteet` take one filter for every type). If LIPAS renames or drops those layers, search loses its routes and stops (Places still work).
- **Traficom's depth layers** are shown "not for navigation" and never used for routing (its licence). If Traficom changes the licence or asks, the layers can be dropped from Paddle's defaults.

## Working on it

The rules are in [AGENTS.md](../AGENTS.md). In short: start from the task the user picked, its work package, or the latest Hand-over, and claim it; one focused pull request may close several related issues, each with its own "Fixes #n", in the issue's milestone; `tools/smoke.py` passes; CHANGELOG updated in the same PR (and a phase's plan); every request through `js/net.js`; share links keep working; and only the user merges.

### Shared controls

Where a screen needs a control that does one of these jobs, it uses this one, with its class (AGENTS.md: one style, and don't redesign what works). A different element is fine where the job is different, once the user has chosen it; then it joins this table. The cards of 25d use them too; [#345's list](https://github.com/TommiContursi/Polku/issues/345#issuecomment-6319843803) has their measurements. Since the design system's controls PR (#382, #356), each job has one look, and `tools/smoke.py controls` measures each pair where the app draws it; the values they take are in [DESIGN.md](../DESIGN.md).

- **A new screen** reuses these for the same jobs. A new control is proposed to the user first, and once chosen it joins this table. 25d's cards propose a few (#355): the plain row with a value, the switch with icons, the warning box and the name field.
- **Every control shares** one focus ring (2 px in `--focus`, set once with `:where(…):focus-visible`, drawn inside a row and a menu's item) and press feedback (`btn`, `tool`, `chip`, `act-chip`, `way-tile`, a switch's buttons and the map's and the top bar's buttons shrink to 97 % for 120 ms while held, with no grey flash; none with reduced motion). A control's own rule may move the ring (its offset), never change its colour or width.
- **Menus and tooltips move** (DESIGN.md's Motion): `popMenu()` and the sport pill's menu (`openActs()`) grow from their button over `--t-open` (`popMenu()` sets `transform-origin` at the button) and leave over `--t-press`; the toolbar's first tooltip (`tooltip()`) grows over `--t-press`, and while one is shown, or was hidden less than 900 ms ago, the next comes at once, with no wait. A menu that's a sheet of its own (`menu-sheet`) only fades. From the keyboard (`:focus-visible` on the button, or in the menu) they come and go at once (`.instant`), the sport pill's chevron too, and so does a menu opened while another is leaving. A closing `popMenu()` is removed at once, so `.menu-pop` is only ever the open menu, and a copy of it (`.menu-leaving`, inert) fades where it was. The sport pill's menu stays in the page when the pill is drawn again (`renderActivityBar()`), so it isn't drawn in again, and hidden it is still drawn while it fades (`allow-discrete`). A new light, dark or contrast (`applyTheme()`) is drawn once with every transition off (`.restyle` on `<html>`, then a forced style pass), so no button fades its colours behind the panels. `tools/smoke.py controls` checks all of it, by a click and by the keyboard, with and without reduced motion.
- **A panel built again on a change** (Layers, its quick drawer, Settings, the speed editor, the sport menu's craft) wraps the rebuild in `settleControls()` (`js/ui.js`): a control that changed starts from how it was drawn (a switch's `checked` attribute; a segment's, a chip's or a tile's `aria-pressed`, a base map's `aria-checked`, a row's `aria-expanded`; a quick tile's look is its `.qt`'s `on` class), so its own transition runs, and the focus goes back to the control it was on. A control is known across the rebuild by its first `data-*` value where it has one (`data-tile`, `data-base`, `data-craft`, `data-k`, `data-appearance`), else by its words. A switch that doesn't rebuild its panel keeps its attribute in step (`toggle()` in `js/main.js`). What opens in a rebuilt panel fades in only on the tap that opened it, through a one-off class (`enter`: Settings' speeds, `speedNew`; Layers' groups, `layerGroup()`), never when the panel is drawn again or from the keyboard; from the keyboard their chevrons turn at once too (`:focus-visible`).
- **A mock-up** copies the CSS of the controls it uses from `css/app.css`, with the same class names, in a marked block (as `docs/plans/mockups/issue-345-map-cards.html` does), so what the user approves is what gets built. When the app's controls change, the copy is made again.
- **No copies:** no second class for a control that exists (a `card-row` beside `way-tile`, say). A variant of one is a modifier on its class, said in this table.
